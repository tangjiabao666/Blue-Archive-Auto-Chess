# 贡献流程与权利边界

## 先确认贡献范围

目前没有为程序源码新增统一开源许可证。公开可见不等于开放所有使用、修改或再分发权利；拟复用或提交较大贡献时请先向项目所有者确认适用授权。这里的贡献说明本身不授予额外许可。

保留 [Godot 许可证](../tools/windows_release/notices/GODOT-LICENSE.txt)、[第三方声明](../tools/windows_release/notices/GODOT-THIRD-PARTY-NOTICES.txt) 和已有文件声明。它们不能授权你再分发原作模型、动画、声音、图标、提取 JSON 或资源派生着色器。私有使用提示同样不是权利人授权。

## 一次改动的建议步骤

1. 先读[架构](ARCHITECTURE.zh-CN.md)，明确改动属于规则、模拟、表现、网络还是发布工具。
2. 用小范围分支修改；记录目标、复现和预期行为。先建立失败测试，再修复，不把重构和资源更新混在同一个无法审查的补丁里。
3. 先跑相关纯源码测试，再在有权使用的完整本地环境跑依赖资源的检查。无法运行的测试明确列出缺失输入，不能写成已通过。
4. 改动存档格式、规则 profile、活动名单、协议或资源布局时，同时检查旧存档、兼容边界和发布流水线的固定计数。不要为让新输入通过而直接放宽安全和完整性门槛。
5. 更新对应文档，说明是否改变手动 EX、胜负判定、联机行为或画质默认值。
6. 提交前检查待提交文件与差异，确认只包含有权公开的代码和文档。

```sh
git status --short
git diff --check
git diff --cached --stat
git diff --cached --name-only
```

`.gitignore` 忽略多数原作资源、data、私有 fixtures、工具链、构建输出和常见密钥；它不能阻止已跟踪文件或强制添加。不要用 `git add -f` 把资源补进公开仓库，也不要提交完整私有仓库历史。

## 新角色和资源变更

完整本地实现至少涉及活动名单与费用、角色技能和表现配置、模型与动画、肖像/图标、普通及技能声音、VFX 事件/时间线/材质、目标规则、存档投影、源数据边界测试及导出依赖门槛。当前计数见 [Windows 构建](../tools/windows_release/README.md)，应以脚本常量和实际清单为准。

`tools/import_roster_snapshot.py` 只导入受支持的准备好快照，不负责全链路激活或权利审查。拟替换为原创/可公开授权资源时，需要重新适配并验证，不能保证把文件改名后即可运行。

## 报告问题和提交补丁

问题报告给出最小复现、期望/实际、版本与环境；补丁说明影响路径、执行过的命令、结果及未验证项。Windows 卡死、性能、声音、LAN 和 Android 问题尤其需要对应设备证据。请勿公开个人目录、账户信息、密钥、私有存档或原作资源本体。

当前仓库的 GitHub Actions 只执行公开源码检查，不自动发布游戏，也不覆盖全部资源与设备回归。新增无需原作资源的测试时，请同步检查 `.github/workflows/source-checks.yml` 的显式测试列表。发布产物是另一步：先完成资源许可审查、完整固定提交构建和目标设备验收，再决定是否分发。
